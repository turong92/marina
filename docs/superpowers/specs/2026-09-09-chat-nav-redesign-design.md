# 대화 탐색 재설계 — 모바일은 드롭다운 하나, 웹은 분할 하나

- 날짜: 2026-09-09
- 상태: **형 검토 대기**
- 선행: `2026-08-11-nondev-room-redesign-design.md` §9-4 (탭 자동 접기를 "넘치면 그때"로 미뤄둔 항목)

## 배경

형: *"상단에 세션 칩 쭉 있고 채팅창 바로 위엔 서브에이전트 쭉 있잖아? 이거 상단에 몰고
드롭다운 같은 형식으로 녹이는 게 나을 것 같은데. 그 안에서 채팅창처럼 최근 대화 왔다갔다한
데가 맨 위로 올라오고. 그러고 누르면 오른쪽 탭에 데스크탑 앱처럼 열리거나."*

이어서: *"대화는 동일 위계로 화면 나누고 서브는 각 화면에 패널로 해서 각각 좌우로 창 조절
가능하면 더 좋을 느낌인데."*

그리고: *"아예 웹이랑 모바일은 의미가 다르지 않을까? A 기반에 채팅방 전환이 편해지면 될 것
같은데."*

### 지금 화면이 실제로 쌓고 있는 것 (실측)

모바일(`marina_mobile.py`):

| 자리 | 무엇 | 형식 |
|---|---|---|
| 헤더 1줄 | `☰` 서랍 = **방 목록** | 서랍(엣지 스와이프·☰) |
| 헤더 2줄 | `roomChats` = **이 방의 대화** | 가로 스크롤 칩, 대화 2개 이상일 때만 |
| 입력창 위 | `sessionControls` = `[모델·기본값] [서브에이전트 N] [상태] [■]` | 버튼 → 바텀시트 |

서브에이전트는 **이미 칩이 아니라 버튼+시트**다(`openSubagents`, `#subagentSheet`). 그래도
형 지적의 핵심은 맞다 — **"다른 대화로 가는 길"이 셋으로 흩어져 있고 형식이 전부 다르다.**

웹:

| | 지금 |
|---|---|
| 대화 (`app-11-chat.js`) | 브라우저식 탭(`chatTabs`). **분할 없음** |
| 터미널 (`app-10-term.js`) | `▭ ▯▯ ⊟ ⊞` 1·좌우·상하·4분할 + 칸 D&D + focus + localStorage |
| 폭 드래그 | 사이드바만 있음(`rail` + clamp + dblclick 복원 + localStorage). **칸 사이는 없음** |

웹 `openChatPicker` 는 `chatAgentsFor(root)` 로 **지금 고른 워크트리 세션만** 보여준다.
다만 `chatTabs` 는 `root` 를 들고 다니고 `showRoot` 분기가 있어, 워크트리를 갈아탄 뒤
추가하면 결과적으로 방이 섞인 탭줄이 된다. 즉 **웹은 이미 "A 기반인데 다른 방 걸 얹으려면
워크트리를 먼저 갈아야 하는"** 상태다.

## 형이 결정한 것

| 항목 | 결정 |
|---|---|
| 대화를 누르면 | 웹 = **칸에 얹는다**(동일 위계 분할) · 모바일 = **전환**(분할이 없으므로) |
| 작업자를 누르면 | **우측에서 들어오는 패널** — 웹은 그 칸 위, 모바일은 전면 |
| 주 무대 | **웹**. 모바일은 접힌 형태로 따라온다 |
| 모바일 분할 | **안 만든다.** 폴드 펼침 정도에서나 쓸 것 |
| 칸에 넣을 범위 | **A 기반 = 같은 방 안.** 대신 방 전환을 싸게 |
| 웹·모바일 관계 | **다른 물건.** 레이아웃 상태를 공유하지 않는다 |
| 대화 vs 서브에이전트 | **같은 목록에 섞지 않는다.** 한 드롭다운 안 두 구역 |

## 관통하는 원칙

> **A 기반(지금 방 안) + 방 전환 비용을 0에 가깝게.**

공유하는 것은 **데이터**(방·대화·서브의 목록과 상태)뿐이다. 화면 구조는 공유하지 않는다 —
웹은 작업대(여러 개 펼쳐놓고 오래 앉음), 모바일은 리모컨(하나씩 확인하고 지시하고 나감).

**"대화를 누르면 무엇이 되나"가 표면마다 다른 이유**도 여기서 나온다. 웹엔 칸이 있으니
대화는 칸에 얹히고(동일 위계), 모바일엔 칸이 없으니 전환된다. 같은 결정의 두 얼굴이지
두 개의 규칙이 아니다. 작업자는 어느 쪽이든 **패널**이다 — 부모 대화에 딸린 기록이라
동일 위계로 놓을 수 없다.

### 구현 순서

**모바일(§2) 먼저, 웹(§3) 다음.** 모바일은 파일 하나(`marina_mobile.py`) 안에서 끝나고
형이 매일 쓰는 화면이라 피드백이 빠르다. 웹 분할은 공통 모듈을 뽑는 일이 끼어 있어
되돌리기가 비싸다. 계획도 둘로 나눠 쓴다.

## §1 — 범위

### 웹 = 작업대

1. 대화 탭에 **분할** `▭ ▯▯ ⊟ ⊞` — 터미널의 `TERM_LAYOUTS`·slots·focus·localStorage 를 재사용
2. **폭 드래그** — 터미널에도 없다. 여기서 만들고 터미널이 나중에 같이 쓴다
3. pane 안 **서브에이전트 = 오버레이** (pane 을 또 쪼개지 않는다)
4. `＋` 피커에 **최근 대화** 구역 — 워크트리를 먼저 갈아야 하는 단계를 없앤다

### 모바일 = 리모컨 (분할 없음)

1. 헤더 **두 줄 → 한 줄**. `roomChats` 칩줄 제거, 트리거 `[결제 플로우 · 기본 ▾ ●2]`
2. 드롭다운 **3구역**: `최근 대화`(방 무관·5개) / `이 방의 대화` / `이 대화의 작업자`
3. 작업자를 누르면 **우측에서 들어오는 전면 패널**. 하단 `[서브에이전트 N]` 버튼 제거
4. `☰` 서랍은 **그대로** — 방 목록. 드롭다운의 `최근 대화` 가 그 지름길

### 화면 폭 규칙 (웹 전용)

**pane 최소 폭 360px 을 못 지키는 레이아웃은 고를 수 없다.**

| 화면 | 폭(대략) | 가능한 레이아웃 |
|---|---|---|
| 폰 세로 / 폴드 접힘 | ~360–390 | `▭` 하나 |
| 폴드 펼침 / 태블릿 | ~700–900 | `▭ ▯▯ ⊟` |
| 웹 | 1200+ | `▭ ▯▯ ⊟ ⊞` |

기기를 판별하지 않는다. 폴드는 펼치는 순간 폭이 넘어가 저절로 분할이 살아난다.
못 고르는 버튼은 **지우지 말고 흐리게 + "화면이 좁아요"** — 사라지면 기능이 없는 줄 안다.

### 안 만드는 것 (일부러)

- 폰 세로 상하분할 · 모바일 분할 일체 (웹이 주 무대로 정해졌다)
- 기기 판별 (폭 하나로 갈린다)
- 방을 넘나드는 드래그앤드롭 (A 기반이라 필요 없다)
- 웹·모바일 레이아웃 상태 공유 (의미가 다르다)
- 분할 칸 전환 단축키

## §2 — 모바일 드롭다운·패널

### 2.1 트리거 (접힌 모습)

```
┌────────────────────────────────────────┐
│ ☰   결제 플로우 · 기본  ▾   ●2   🔔  ⊙ │
└────────────────────────────────────────┘
      └───────┬──────┘  └┬┘
       방 · 대화 이름     안 보이는 것들의 요약
```

- 방 이름과 대화 제목이 **같으면 하나로 접는다** (nondev-room 스펙 §2 의 중복 제거 규칙 재사용
  — 카드가 이름을 세 번 반복하던 그 문제와 같은 뿌리)
- 배지는 **가장 센 상태 하나 + 개수**. 우선순위는 기존 그대로 `문제 > 응답필요 > 작업중`.
  세는 대상은 **지금 화면에 안 보이는 대화들**뿐이다. 아무것도 없으면 그리지 않는다
- 이 배지가 칩줄을 지우면서 잃는 상태 가시성의 **보전분**이다. 없으면 순수 후퇴다

### 2.2 세 구역

```
▾ 최근 대화              ← 방 무관, 5개
   ● 결제 플로우 · 기본        지금  ✓
   ● 날씨 재설계 · 기본        4분
   ! 소셜 로그인 · 리뷰        12분  응답필요
  ────────────────────────
  이 방의 대화            ← 대화 1개면 구역째 숨김
   ● 기본                     지금  ✓
   ○ 디자인 손보기            어제
  ────────────────────────
  이 대화의 작업자         ← 없으면 구역째 숨김
   ▸ Explore: 결제 API        완료
   ▸ code-review             실행중
```

- 대화를 누르면 **전환**, 작업자를 누르면 **패널**. 구역이 갈려 있으니 누르기 전에 결과를 안다
- `최근 대화` 의 "최근" = **내가 마지막으로 연 시각**(브라우저 탭·앱 전환기와 같다).
  서버 활동순이 아니다 — 활동순이면 내가 안 건드린 게 위로 튀어오른다
- **단, 응답필요는 5개 밖이어도 끌어올린다.** 물어봐 놓고 기다리는 대화를 놓치면 안 된다.
  자리는 가장 오래 안 본 것이 내준다

### 2.3 열려 있는 동안 순서를 바꾸지 않는다

폴이 3초마다 돈다. 열린 채 재정렬되면 **누르려던 게 도망간다.**

| 열려 있는 동안 | |
|---|---|
| 상태 dot·라벨 | **갱신한다** (죽은 화면을 보여주지 않는다) |
| 순서·항목 구성 | **고정한다** (여는 순간 스냅샷) |
| 새로 생긴 대화 | 끼워넣지 않는다 — 닫았다 열면 나온다 |

기존 `render()` 진입 defer + focusout flush 가드와 같은 정신이다.

### 2.4 뒤로가기

오버레이가 둘 늘어나므로 **스택 하나로 관리**한다.

```
목록 → 채팅 → [드롭다운] → [패널]
        ←back    ←back      ←back
```

안드로이드 뒤로가기로 드롭다운/패널만 닫히고, 한 번 더 눌러야 채팅을 나간다.

### 2.5 패널이 열린 채 대화를 바꾸면 → 패널을 닫는다

작업자는 **부모 대화의 소유물**이다. 따라가면 남의 기록을 남의 대화 옆에 붙여 보여주는
셈이라 거짓말이 된다.

## §3 — 웹 분할·폭 드래그

### 3.1 상태 모양

```js
chatLayout = '1' | 'lr' | 'tb' | '4'      // 형이 고른 것 (저장)
chatSlots  = [tabKey|null, ×4]            // 탭을 가리킨다 (대화가 아니라)
chatFocus  = 0..3
chatFrac   = { col: [0.5, 0.5], row: [0.5, 0.5] }
// → localStorage 'marinaChatLayout'
```

**slots 가 탭을 가리키는 것이 핵심이다.** 터미널이 정확히 이 구조(사이드바=세션 목록 /
그리드=배치)라, 탭 닫기·추가와 분할이 싸우지 않는다. 탭을 닫으면 그 칸만 비고 레이아웃은
흔들리지 않는다.

### 3.2 재사용 경계

| | |
|---|---|
| **공통 모듈로 뽑는다** | `TERM_LAYOUTS`(`{1:[1,1], lr:[2,1], tb:[1,2], 4:[2,2]}`) · 그리드 CSS · **리사이저**(사이드바용을 일반화) |
| **규칙만 베낀다** | `termPlace` 의 배치 규칙 — *"이미 떠 있으면 포커스만 / 빈 칸 있으면 거기 / 없으면 focus 칸"* |
| **가져오지 않는다** | xterm·PTY 부착(대화는 `chat-render.js`) · D&D(§1에서 뺐다) |

`TERM_LAYOUTS` 를 복사하지 않고 뽑는 이유: 값이 갈리면 **버튼 개수와 칸 개수가 어긋난다** —
터미널이 이미 `if (termFocus >= termSlotCount()) termFocus = 0` 로 막고 있는 사고다.

### 3.3 고른 레이아웃과 그리는 레이아웃을 나눈다

§1 의 최소폭 규칙을 구현하는 자리이자, 이 설계에서 **유일하게 새로 판단해야 하는 곳**이다.

```
chatLayout      = 형이 고른 것          ← 저장한다
effectiveLayout = 폭이 허락하는 최대     ← 파생, 저장하지 않는다
```

`ResizeObserver` 로 컨테이너 폭을 재서 `폭 / cols < 360px` 이면 접는다.

- 폴드를 **접으면** `lr` → 실제로는 `1` 로 그려진다 (고른 값은 `lr` 로 남는다)
- 폴드를 **펴면** 아무것도 안 눌러도 `lr` 로 돌아온다

이걸 나누지 않으면 창을 한 번 줄였다 늘렸을 때 형 설정이 영구히 `1` 로 뭉개진다.

### 3.4 폭 드래그

```
┌──────────┬╫┬──────────┐     lr·4 → 세로 구분선
│          ║ │          │     tb·4 → 가로 구분선
│          ║ │          │     4    → 축마다 하나씩(교차점 드래그는 만들지 않는다)
└──────────┴╫┴──────────┘
```

- `gridTemplateColumns: ${a}fr ${b}fr` 로 반영, `chatFrac` 에 저장
- **최소 360px 은 드래그로도 못 깬다** — 구분선이 거기서 멈춘다
  (사이드바의 `Math.max(140, Math.min(420, …))` 와 같은 방식)
- **더블클릭 = 50:50 복원** (사이드바 `rail.ondblclick` 과 같은 관습)
- 드래그 중에는 `chat-render` 재렌더를 하지 않는다 — 매 픽셀마다 트랜스크립트를 다시 그리면
  끊긴다

### 3.5 서브에이전트 오버레이

pane 안에서 `position:absolute; inset:0` 로 **그 칸만** 덮는다.

4분할에서 칸이 360px 이면 오버레이도 360px 라 읽기 힘들다. 그래서 오버레이 헤더에
**`⤢ 넓게`** 하나 — 누르면 잠깐 `1` 로 접어 전체 폭에서 보고, 닫으면 원래 레이아웃으로
돌아온다. 한 줄짜리 탈출구지만 없으면 4분할에서 서브가 사실상 못 읽힌다.

### 3.6 포커스와 입력창

각 pane 에 **자기 입력창**을 둔다. 입력창이 눈에 보이는 것 자체가 "어디에 말하는가"의
표시다(터미널은 입력창이 하나뿐이라 focus 로 갈라야 했다). focus 칸은 터미널과 같은
`.focus` 테두리.

## 검증

`marina_mobile.py` 안 JS 는 이미 `// ROOM_TABS_START (테스트가 이 블록을 vm 에 싣는다)`
패턴으로 노드 vm 테스트를 붙이고 있다. 같은 방식으로 잠근다.

### 모바일

| 무엇 | |
|---|---|
| 정렬 고정 | 스냅샷 뒤 상태를 흔들어도 순서·개수 불변 |
| 응답필요 끌어올림 | 6번째 응답필요가 5개 안에 들어온다 |
| 배지 | `문제 > 응답필요 > 작업중` 우선순위 · **안 보이는 것만** 센다 |
| 뒤로가기 스택 | 드롭다운→패널→back×2 가 채팅에 머문다 |
| 구역 숨김 | 대화 1개 · 작업자 0개 |
| 패널 정리 | 대화를 바꾸면 패널이 닫힌다 |

### 웹

| 무엇 | |
|---|---|
| 레이아웃 가능 판정 | `폭/cols ≥ 360` |
| 접힘/복귀 | 좁혔다 넓히면 `chatLayout` 이 원래 값 |
| `chatFrac` 클램프 | 최소폭 밖으로 못 간다 |
| 복원 시 없는 칸 | `chatFocus >= slotCount` 보정 (터미널이 이미 겪은 버그) |

| 실 브라우저 | Aside 로 드래그 → 새로고침 후 비율 유지 |

## 미결 / 후속

- **§3.3 이 형 감각에 맞는지** — 폴드 접었다 펴는 게 실사용이라 여기가 제일 중요하다
- `최근 대화` 5개는 고정값. 넘치는 실사용이 나오면 그때 조정
- 터미널이 새 공통 리사이저로 갈아타는 것은 **후속** — 이번엔 대화만 쓰고, 터미널은
  동작이 같은 걸 확인한 뒤 옮긴다
- (별건, 이 스펙 밖) 공유 박스에서 `compose_project_name` 이 `main` 체크아웃끼리 겹친다 —
  `<project>-main` 이 전원 동일. 팀이 워크트리만 쓰는 동안은 안 터진다
