# 비개발자 친화 재설계 — Room 을 1급으로, 어드민·멤버 한 모델 위에

- 날짜: 2026-08-11 (2026-08-17 개정)
- 상태: **개정본 — 형 검토 대기**

## 배경

형이 두 가지를 동시에 말했다. **"비개발자가 직접 일을 시킬 수 있어야 한다"** 와 **"나도 헷갈린다"**.
뒤엣말이 핵심이다. 비개발자용 화면만 새로 만들면 형이 보는 화면은 그대로 헷갈린 채 남는다.

헷갈림의 뿌리는 UI 가 아니라 **데이터 모델이 새는 것**이다. 서버가 조각(워크트리·세션들·상태·
링크)을 따로 주고 화면이 그걸 이어붙이니 카드 한 장이 이렇게 나온다:

```
[Claude]  결제 플로우 정리 (쿠폰/구독)          ● 유휴  4일
          claude · mdc-main · 결제 플로우 정리 · mdc-main · payment-flow-coupon-subscription-d023fc
```

이름이 세 번 반복된다. 워크트리 제목과 세션 제목이 **둘 다 "첫 사용자 메시지"에서 나오기 때문**에
거의 같은 문자열이고, 끝엔 해시 붙은 슬러그가 달린다. 워크트리가 대화인지 세션이 대화인지
구분할 근거가 화면에 없다.

관련 코드: `marina_mobile.py` 의 `sessionCard`(제목=`session.title`), `sessionSubtitle`
(부제=`{source} · {alias · sessionTitle · projectLabel · id}`).

## 형이 결정한 것

| 항목 | 결정 |
|---|---|
| 비개발자의 역할 | **직접 일을 시킨다** (관전이 아니다) |
| 채팅방 1개 = ? | **일감(워크트리)**. 세션은 그 방 안의 **탭**이다 (2026-08-17 개정) |
| "일이 끝났다"의 형태 | **미리보기 링크** |
| "완료" 판정 | **멈춤 + 바뀐 파일 있음** (2026-08-17 결정) |
| 새 방 생성 | 비개발자도 만든다. 단 **프로젝트만 고르고 브랜치는 자동** |
| 개발자 기능 분리 | **계정 역할로 자동** (`admin` / `member`) |
| 멤버 표면 / 어드민 표면 | **모바일 / 웹 대시보드** (2026-08-17 결정) |
| 어드민 화면 | **같이 정리한다** — 멤버만 바꾸면 의미 없다 |
| 어드민의 불편 | **네 가지 전부**: 카드 정보 과다 · 이름 중복 · 목록 김 · 탭 혼란 |
| 배포 권한 | 나중에 비개발자가 질 수도 있다 → **자리만** 만들어 둔다 |
| 웹·모바일 대화창 | **모바일을 기준으로 웹을 고친다** ("웹은 터미널 같아서 눈에 안 들어온다") |
| 방 화면에 보일 것 | 지금 뭐 하는 중인지 · 뭔가 바뀌었는지 요약 · 대화만 깔끔하게 |
| Room 도입 범위 | **Room 이 원본**, 기존 표면은 파생 (2026-08-17 결정) |
| 치우기 | **아카이브 + 삭제 둘 다**. 모바일 '숨김'은 아카이브로 흡수. 멤버도 자기 방은 삭제(미커밋이면 경고). 대화 하나만 지우는 것도 있다 (2026-08-17 결정, §7) |

미리보기 버튼을 "방 화면에 상시" 로는 고르지 않았다. 완료 신호로는 필요하지만 늘 떠 있을
필요는 없다는 뜻으로 읽고, **완료 카드 안**에 넣는다(§2).

## 설계

### 1. Room — 서버의 1급 개념이자 **유일한 원본**

서버가 조립까지 끝낸 뷰모델을 준다. 화면은 받아서 그리기만 한다.

```
Room {
  id, name,          # 사람이 붙인 이름 하나. 슬러그·해시는 노출하지 않는다
  project,           # 프로젝트 라벨
  status,            # 대기 | 작업중 | 응답필요 | 완료 | 문제  (5개 고정, §5)
  previewUrl,        # 있을 때만
  lastMessage, lastAt,
  canShip,           # 지금은 항상 false. 배포 버튼의 자리(§확장 지점)
  archived,          # 접어둔 방인가 (§7)
  canDelete,         # 이 사람이 이 방을 지울 수 있나. 서버가 역할·소유자로 판정해서 준다(§7)
  dirty,             # 미커밋 변경이 있나. 삭제 경고와 §4 완료 판정이 같이 쓴다
  tabs: [            # 방 안의 세션들. 0개일 수도 있다(아직 아무도 말 안 건 워크트리)
    { id, source, title, status, primary, canDelete }
  ]
}
```

**Room 이 진실이고 기존 구조는 파생이다.** 서버가 워크트리·세션·상태를 읽어 Room 을 먼저
계산하고, 지금의 `/mobile/api/state` 세션 목록은 **그 Room 목록을 평탄화해서 만든다**. 반대
방향(세션 목록에서 Room 을 조립)이 아니다.

반대로 하면 두 벌이 생기고 상태 판정이 또 갈라진다 — 지금 겪는 문제가 정확히 그거다.
(옛 스펙 §미해결 4번 "병행할지 대체할지"는 이 결정으로 **해소**. 병행이 아니라 파생이다.
기존 응답 스키마는 유지되므로 화면을 한꺼번에 갈아엎을 필요는 없다 — 계산 경로만 뒤집는다.)

### 2. 방 = 워크트리, 세션 = 방 안의 탭

**옛 스펙(§1 "세션은 Room 안으로 완전히 숨는다 / 워크트리=Room=대화 1:1:1")을 뒤집는다.**

숨기는 안은 "세션이 여럿이면 최신 것을 골라 이어붙인다"였는데 실제 워크트리는 그렇게 안 굴러
간다. 같은 일감 안에서 claude 로 하나 codex 로 하나 돌리거나 긴 작업을 끊어 새 세션으로 이어
가는 게 흔하다. 최신 하나만 보여주면 나머지 대화는 **사라진다** — 숨기는 게 아니라 잃는 거다.

- **방 = 워크트리 1개.** 이건 유지한다. 일감의 단위는 워크트리가 맞다.
- **세션 = 방 안의 탭.** 여러 개면 여러 개로 보인다. 브라우저 탭과 같은 멘탈 모델이고, 이미
  웹 대화 워크스페이스가 쓰는 모델이다(2026-08-09 작업).
- **방의 `status` 는 탭들의 상태를 하나로 접은 것.** 우선순위는 `문제 > 응답필요 > 작업중 >
  완료 > 대기` — 방 목록에서 놓치면 안 되는 순서, 즉 사람 조치가 필요한 걸 위로 올린다.

**멤버에게 어디까지 보이나.** 멤버는 탭을 의식하지 않는다.

- 탭이 1개면 **탭줄 자체가 없다.** 방을 열면 곧장 대화다. 대다수가 이 경우다.
- 2개 이상이면 대화 위에 **얇은 전환줄** 하나. 이름은 사람말 제목이고 `claude`/`codex` 같은
  엔진 이름·sid 는 안 보인다. 방을 열면 `primary`(마지막 활동이 가장 최근인 탭, 서버가 고른다)
  가 먼저 열린다 — 멤버가 쓰던 대화가 그대로 열리는 게 자연스럽다.
- 멤버는 탭을 **만들지 못한다.** 새 대화가 필요하면 새 방을 만든다. 탭이 늘어나는 건
  어드민이 그 일감에 손을 댔을 때뿐이다. (지우는 건 자기 방에 한해 된다 — §7)

**이름 규칙**: `name` 은 사람이 읽는 한 줄이고 워크트리 슬러그(`payment-flow-...-d023fc`)는
상세에서만 보여준다. 중복은 서버가 제거해서 준다 — 탭 제목이 방 이름과 같으면 접는다
(§배경의 "이름 세 번" 이 여기서 다시 나오면 안 된다).

### 3. 표면 — 모바일 = 멤버, 웹 = 어드민

멤버 화면과 어드민 화면은 **다른 모델이 아니다** — 같은 Room 위에 도구를 얹은 형태다. 다만
**어디서 쓰는지는 나눈다**:

| | 멤버 | 어드민(형) |
|---|---|---|
| 주 표면 | **모바일** | **웹 대시보드** |
| 보이는 것 | 방 목록 + 대화 | 같은 방 목록 + 대화 + 도구 서랍 |
| 도구(로그·깃·연결·터미널·서비스) | 없음 | 서랍 안에 |

분기는 **역할로 자동**이다(`auth.db` 의 `admin`/`member`). 화면을 고르는 스위치가 아니라
로그인한 사람이 누구냐로 갈린다 — 멤버는 모드가 있다는 것도 모른다.

**어드민이 모바일로 들어와도 막지 않는다.** 다만 도구 서랍의 주 무대는 웹이다 — 서랍에 들어가는
로그·깃 그래프·터미널·compose 는 폰에서 제대로 쓸 물건이 아니다. 모바일의 어드민에게는 방
목록과 대화, "지금 상태" 정도만 온전히 준다.

#### 멤버 화면 (모바일)

```
┌──────────────────────────────┐
│ ← 결제 플로우 정리            │
│ [기본]  [디자인 손보기]        │  ← 탭이 2개 이상일 때만 나온다
├──────────────────────────────┤
│                              │
│        (대화만 깔끔하게)       │
│                              │
├──────────────────────────────┤
│ ⚙ 파일 3개 고치는 중…         │  ← 지금 뭐 하는 중인지 (한 줄, 사람말)
├──────────────────────────────┤
│ 메시지 입력…              [↑] │
└──────────────────────────────┘
```

- **진행 표시는 한 줄, 사람말로.** 도구 이름·명령어·경로는 보이지 않는다.
- **완료 카드**: 일이 끝나면 대화 안에 카드가 하나 떨어진다. "뭐가 바뀌었는지" 요약 +
  **[화면 보기]** 버튼(= `previewUrl`). 판정 규칙은 §4.
- 서비스·로그·깃·터미널·연결·compose 는 **없다**.
- **새 일감**: `+` → 프로젝트 하나만 고른다. 브랜치명은 마리나가 첫 메시지에서 짓는다.
  선택지를 프로젝트 하나로 줄이는 게 안전장치다.

#### 어드민 화면 (웹)

| 형의 불편 | 대응 |
|---|---|
| 카드 하나에 정보가 너무 많다 | 카드는 **이름·상태·마지막 활동** 셋만. 서비스·에이전트는 방 안으로 |
| 이름이 중복·무의미 | Room `name` 하나만. 슬러그·해시는 상세에서만 |
| 목록이 너무 길다 | 기본 **최근 활동순 + 진행 중만**. 끝난 건 접어둔다 |
| 탭이 많고 어디서 뭐 하는지 | 방 안은 **대화 중심**, 개발 도구는 **접힌 서랍 하나**로 |

마지막 줄에 주의. **여기서 없애는 "탭"은 도구 탭**(로그·깃·연결·터미널·서비스)이고, §2 의
**대화 탭은 다른 물건**이다. 도구 다섯 개를 늘 펼쳐두는 걸 서랍 하나로 접고 대화는 탭으로
둔다 — 대화는 계속 오가는 것이고 도구는 필요할 때만 여는 것이라서다.

### 4. "완료" 판정 — 멈춤 + 바뀐 파일

**에이전트가 멈췄고(작업중이 아니고) 워크트리에 변경된 파일이 있을 때** 완료로 본다.
멈추기만 하고 바뀐 게 없으면 완료 카드를 만들지 않는다.

옛 스펙 §미해결 2번("첫 판은 `completed` 로 두고 오탐이 잦으면 다시 본다")을 이 규칙으로
**대체한다**. `completed` 만으로는 오탐이 확실하다 — 질문만 하고 끝난 턴, "그건 못 합니다"로
끝난 턴, 설명만 한 턴이 전부 `completed` 다. 그때마다 "일 끝났어요, 화면 보세요" 카드가
떨어지면 카드 자체를 안 믿게 된다.

**바뀐 파일**은 미커밋 변경 + base 보다 앞선 커밋을 합쳐서 본다. 어느 쪽이든 "볼 만한 결과"가
생긴 상태이고, 커밋까지 끝낸 경우를 빼먹으면 안 된다.

### 5. status 5개 — 지금 어휘를 접어서 만든다

지금 코드의 상태 어휘는 6개다: `working` · `idle` · `completed` · `blocked` · `failed` ·
`waiting`. 판정의 단일 캐논은 `marina_sessions.py` 의 `resolve_session_liveness` 다(확인함:
`merge_agent_status` 병합 → 프로세스 없으면 강등 → `completed`+PTY 살아있으면 `waiting` 승격).

새 어휘를 만들지 않는다. **그 6개를 5개로 접기만 한다** — 캐논을 그대로 두고 표시층에서만
접으면 상태 판정이 또 갈라질 일이 없다.

| 지금 어휘 | Room status | 근거 |
|---|---|---|
| `working` | **작업중** | 그대로 |
| `idle` | **대기** | 아무것도 안 돌고 있음. 다음 지시를 기다리는 상태 |
| `blocked` | **응답필요** | `permission_prompt`·`elicitation_dialog` 만 남은 blocked = 사람이 답해야 진행된다 |
| `waiting` | **응답필요** | 프로세스가 살아서 입력을 기다림. **멤버 관점에선 blocked 와 구분이 없다** — 둘 다 "내가 뭔가 해야 함". 어드민 서랍에서는 원어휘를 그대로 보여준다 |
| `failed` | **문제** | 그대로 |
| `completed` | **완료** 또는 **대기** | §4 로 갈린다. 바뀐 파일 있으면 완료, 없으면 대기 |

애매한 자리 둘:

- **`waiting` → 응답필요**: 코드 주석상 `waiting` 은 "턴을 끝내고 프롬프트에서 대기"(빨강 아님)
  라 `blocked` 보다 순하다. 그래도 멤버에게 요구하는 행동은 같다 — 뭔가 쳐야 움직인다. 색만
  `blocked` 진하게 / `waiting` 옅게 두어 어드민이 구분한다.
- **`completed` → 대기**: 어색해 보이지만 멤버가 할 일이 정확히 "다음 지시"라 대기가 맞다.
  여기에 상태를 하나 더 만들면 5개 고정이 깨지고, 멤버는 그 차이로 할 수 있는 게 없다.

### 6. 웹·모바일 대화창 통일

렌더러는 이미 `marina-web/chat-render.js` 로 공유돼 있다(2026-08-03 작업). 벌어져 보이는 건
**웹이 그 위에 터미널풍 스타일을 덮어쓰기 때문**이다. 로직이 아니라 **웹 CSS 를 걷어내 모바일
말풍선 스타일로 맞추는** 작업이라 분량이 작다.

### 7. 치우기 — 아카이브 · 대화 삭제 · 방 삭제

형이 짚은 구멍이다. 지금 스펙엔 방을 **만들고 쓰는** 얘기만 있고 **치우는** 얘기가 없다.
확인한 현재 상태: 워크트리 삭제는 **웹에만** 있고(`app-5b-actions.js` 의 `removeWorktreeFlow`
→ `/api/remove-worktree` → `marina_lifecycle.remove_worktree`), 대화 삭제는 **어디에도 없고**,
모바일에만 '숨김'이 있다(`mobile_set_hidden`, `hidden-sessions.json` 에 `source:sid` 키 목록).

세 층위로 나눈다. **되돌리기 비용 순서**로 갈랐다 — 사람이 실수했을 때 잃는 게 다르기 때문이다.

| | 무엇이 사라지나 | 되돌리기 | 누가 |
|---|---|---|---|
| **아카이브**(방) | 목록에서만 접힌다 | 1탭 | 멤버·어드민 |
| **대화 삭제**(탭) | 그 탭이 마리나에서 사라진다. 워크트리는 그대로 | 없음(원본은 남음) | 어드민, 자기 방이면 멤버 |
| **방 삭제**(워크트리) | 폴더·브랜치까지 | **없다** | 어드민, 자기 방이면 멤버 |

**모바일의 '숨김'은 아카이브로 흡수한다.** 비슷한 개념 둘을 따로 둘 이유가 없고, 지금 숨김은
세션 키 단위라 §2 의 "방이 단위" 와도 어긋난다. 기존 `hidden-sessions.json` 은 방 단위 아카이브
저장소로 승계하되, 한 방의 세션이 전부 숨김일 때만 그 방을 아카이브로 옮긴다(1회성 이관,
실패해도 잃는 게 없다).

**아카이브의 의미.** 목록에서 빠지되 **'전체 보기'에는 나온다** — 이미 그렇게 굴러가는 축이
있다. `AGENTS_MAX_AGE`(7일) 로 기본 목록을 자르고 `AGENTS_MAX_AGE_ALL`(90일) 로 전체를 훑는다.
아카이브는 그 **암묵적 시간 규칙을 사람이 손으로 당기는 것**이지 새 축이 아니다.
새 활동이 생기면 **자동 복귀한다** — `archivedAt` 을 적어두고 `lastAt > archivedAt` 이면 푼다.
근거: 아카이브는 "지금 안 볼 것"이지 "죽은 것"이 아니다. 접어둔 방에서 에이전트가 다시 움직여
`응답필요`(§5)가 떴는데 목록에 없으면 그걸 놓친다. 웹 카드의 **"삭제 권장"** 칩
(`clean · 미머지 0 · 7일↑ 미활동`, `app-5-sessions.js`)은 **아카이브 자동 제안**의 조건으로
쓴다. 자동으로 접지는 않는다 — 판정이 틀렸을 때 형이 방을 잃은 것처럼 느낀다.

**"대화를 지운다"가 무슨 뜻인가.** 워크트리는 폴더를 지우면 끝이지만 대화의 원본은 마리나 밖에
있다(`~/.claude/projects/<슬러그>/<sid>.jsonl`, codex 는 `~/.codex/sessions/**/rollout-*.jsonl`).
**기본은 "마리나에서만 치우기"** 다. 목록·탭에서 사라지고, CLI 로 `claude --resume <sid>` 하면
그대로 이어진다.

여기 함정이 하나 있다. 마리나는 세션을 **파일 스캔으로 발견한다**(`_claude_cli_sessions` 가
`~/.claude/projects/*/*.jsonl` 을 훑는다). 그래서 "목록에서 뺀다"는 잊는 걸로는 안 되고 **묘비
목록을 저장해야** 한다 — 다음 폴링에 다시 살아난다. 숨김이 이미 그 방식이니 그 자리를 쓴다.

**원본 삭제는 1차 범위 밖으로 뺀다.** 어드민 전용으로도 두지 않는다. 근거 셋: ① 되돌릴 수 없다
② 마리나가 **남의 도구 데이터**를 지우는 것이라 사용량·재개·감사 근거가 통째로 없어진다
③ 형 혼자 쓰는 버튼 하나에 그만한 위험을 붙일 이유가 없다 — 정말 지울 거면 `rm` 이 더 정직하다.
대신 삭제 확인창에 **원본 경로를 보여준다**. 지우고 싶으면 형이 직접 지우면 된다.

**멤버가 자기 방을 지우는 것 — 권한은 이미 있다.** 확인한 사실: `/api/remove-worktree` 는
`_ROOT_POST_PATHS` 에 있어 `_require_root_access` → `AccessPolicy.can_root` 를 통과해야 하고,
`can_root` 는 어드민이거나 `resource_owners('worktree', <절대경로>)` 의 소유자면 참이다. 그 소유자
행은 대시보드로 워크트리를 만들 때 기록된다(`marina_handler.py` 의 `worktree.create`).
**즉 "자기 방" 판정은 지금 스키마로 된다.** 새로 만들 건 모바일 UI 뿐이다.

부수 효과 하나가 안전장치로 붙는다 — CLI 나 손으로 만든 워크트리엔 소유자 행이 없어서 멤버에겐
**애초에 보이지 않는다**. 멤버가 형의 작업물을 지울 경로가 구조적으로 없다.

**미커밋 변경 — 막지 않고, 먼저 보관하고 지운다.**

초안은 "멤버에게는 `force` 를 주지 않는다(차단하고 형에게 물어보게 한다)" 였다. 형이 그 자리를
정확히 짚었다 — *"내가 무조건 보는것도 아닐거같은데"*. 차단은 **사람의 주의력에 기대는 설계**다.
형이 안 보면 그 방은 영영 안 치워지고, 멤버는 할 수 있는 게 없다.

목표를 다시 보면 "삭제를 막는 것"이 아니라 **"작업을 잃지 않는 것"** 이다. 그러면 막을 게 아니라
**지우기 전에 잃을 게 없는 상태로 만들면** 된다.

```
멤버가 방 삭제 → 미커밋 변경 발견
  → 마리나가 그 변경을 wip/<방이름>-<날짜> 브랜치로 커밋 (untracked 포함)
  → 워크트리 폴더 삭제
  → 보관 브랜치는 남는다
```

**이게 성립하는 근거**(확인함): `remove_worktree` 의 브랜치 정리는 `delete_merged_branch` 라
**머지 안 된 브랜치는 지우지 않는다**. 즉 커밋만 되어 있으면 폴더가 사라져도 작업은 브랜치에
그대로 남는다. 새 배관이 필요한 게 아니라 **삭제 직전에 커밋 한 번**을 끼우는 것이다.

**보관은 `wip/` 전용 브랜치로 뺀다**(형 결정). 원래 브랜치(`claude/<id>`)에 얹으면 그 브랜치의
이력에 "치우다 만 상태" 가 섞인다. 이름에 방 이름과 날짜가 들어가면 **보관본이라는 게 이름에서
드러나고**, 형이 나중에 목록만 봐도 무엇을 건질지 안다.

**멤버 화면은 그냥 "지웠어요" 라고만 한다**(형 결정). 멤버는 git 을 모르므로 "따로 저장해뒀어요"
는 안심이 아니라 물음표를 남긴다 — 무엇이 어디에 저장됐는지 되물을 수 없는 사람에게 그 문장은
정보가 아니다. 보관 사실은 어드민 쪽(방 목록의 `wip/` 브랜치, 삭제 감사 로그)에서 드러난다.

**어드민 웹은 지금 동작을 유지한다** — 경고 후 `force` 로 폐기까지. 형은 git 을 알고, 정말로
버리고 싶은 경우가 있다. 자동 보관은 **멤버 경로에만** 붙인다.

**신규 작업과 이미 있는 것.**

- 이미 있음: 웹 워크트리 삭제(경고·고아 처리·`force`), 소유자 판정과 API 권한 게이트,
  7일/90일 접기, 미머지 브랜치 보존(`delete_merged_branch`)
- 신규: 방 아카이브(상태·저장·자동 복귀), 대화 삭제(묘비 저장 + API + 웹/모바일 UI),
  모바일 방 삭제, **삭제 전 자동 보관 커밋(`wip/` 브랜치)**, 숨김 → 아카이브 이관

## 해결됨 — 미리보기를 폰에서 열기

옛 스펙은 이걸 **선행 과제**로 적어뒀다. **그 사이 구현돼 동작한다.** 확인한 사실:

- `marina_state.py`: `_PREVIEW_PORT` 기본 **3903**, `_PREVIEW_PUBLIC_PORT` 기본 **8443**
- `marina_handler.py`: `/preview/<label>/<경로>` 를 게이트웨이로 넘기는 `_serve_preview` 가
  **GET·POST 모두** 처리한다. 인증 통과 뒤에 놓여 있다(`/preview` 는 `PUBLIC_PREFIXES` 가
  아니라서 로그인 없이는 도달하지 못한다)
- 3903 이 실제로 리스닝 중이고, Funnel 로 폰에서 열리는 것이 확인됐다

풀린 경로는 옛 스펙이 골랐던 **1번 안(대시보드를 통한 프록시)** 이다. 인증이 이미 걸린 문
하나만 쓰고, 경로 전체를 넘기므로 첫 화면 뒤에 따라오는 JS·CSS·API 요청도 같은 문을 통과한다.

```
폰 → (Funnel 8443) → 마리나 미리보기 :3903 → 게이트웨이 → 워크트리의 앱
       공개·로그인 있음        경로 프록시        라우팅함      이미 떠 있음
```

**남은 잔여 항목**: 옛 스펙이 경고한 **절대경로 위험은 여전히 유효하다.** 앱이 `/static/...`
같은 절대 경로를 쓰면 `/preview/<label>/` 접두사 아래에서 어긋난다(연결 재설계 때 남긴 "잔여
물리" 두 건 중 하나). `marina_handler.py` 주석에도 경로 접두사로는 안 되는 앱(Dozzle 처럼
`base:""` 로 자기 기준을 잡는 것)이 있다고 적혀 있다. 어긋나는 앱은 방마다 주소를 따로 주는
방식(서브도메인)으로 돌린다. 앱을 실제로 띄워봐야 드러나는 종류의 문제다.

## 확장 지점 — 배포

지금은 만들지 않는다. 대신 Room 에 `canShip` 을 두어 자리를 잡아둔다. 나중에 비개발자가 배포를
지게 되면 이 값이 조건을 만족할 때 방 안에 **[반영하기]** 버튼이 뜨는 식으로 붙인다.

지금 만들지 않는 이유: 배포는 사고 시 파급이 크고, 어떤 조건에서 허용할지(리뷰 통과? 테스트
통과? 프로젝트별 정책?)가 아직 정해지지 않았다. 자리만 잡아두면 나중에 UI 를 다시 안 짜도 된다.

## 역할 분리 — 이미 있는 것을 쓴다

`auth.db` 에 `role TEXT NOT NULL CHECK (role IN ('admin','member'))` 와 `project_access`
테이블이 **이미 있다**. 새로 만들 게 아니라 렌더 경로에 연결만 하면 된다.

- `member` 로 로그인 → 방 목록 + 방 화면만 (모바일)
- `admin` 로그인 → 같은 화면 + 도구 서랍 (웹)
- 멤버는 모드가 있다는 것도 모른다. 형은 필요하면 전환할 수 있다

## 미해결 · 리스크

1. **브랜치 자동 작명의 품질** — 비개발자의 첫 메시지에서 브랜치명을 짓는데, 오작명이 쌓이면
   형이 나중에 정리해야 한다. 규칙(날짜 접두사 + 짧은 슬러그)과 나중에 이름 바꾸기를 함께 둔다.
2. **미리보기가 항상 있지는 않다** — 서비스가 없는 워크트리(문서 작업 등)엔 `previewUrl` 이
   없다. 그때 완료 카드는 요약만 보여준다.
3. **"바뀐 파일" 계산 비용** — §4 판정에 워크트리마다 git 상태를 봐야 하는데, 방 목록을 폴링할
   때마다 전부 돌리면 부담이다. 캐시를 어디 둘지는 계획 단계에서 정한다.
4. **탭이 많아지는 방** — §7 의 대화 삭제로 **부분 해소**. 손으로 치울 길은 생겼다. 남은 건
   ① 어드민이 세션을 계속 새로 파는 방에서 전환줄이 넘치는 것 ② 아무도 안 치울 때다.
   자동 접기(오래된 탭을 `⋯` 뒤로)는 실제로 넘치는 방이 나오면 그때 붙인다.
5. **절대경로 미리보기** — §해결됨의 잔여 항목. 앱별로 드러난다.
6. **보관 브랜치가 쌓인다** — §7 의 자동 보관(`wip/<방>-<날짜>`)은 잃지 않게 해주지만 아무도
   안 치우면 브랜치 목록이 길어진다. 지금은 그대로 둔다 — 잃는 것보다 쌓이는 게 낫고, 어차피
   형만 보는 목록이다. 실제로 거슬리면 "오래된 보관 브랜치 정리" 를 어드민 도구로 붙인다.
7. **보관 커밋이 실패하면** — 디스크가 찼거나 훅이 커밋을 막는 등으로 커밋이 실패할 수 있다.
   그때는 **삭제를 진행하지 않는다**(잃을 게 있는 상태로 지우면 안 된다). 멤버에게는 "지금은
   지울 수 없어요" 로 말하고, 어드민에게 알림이 가야 하는지는 계획 단계에서 정한다.
