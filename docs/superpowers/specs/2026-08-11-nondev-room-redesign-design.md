# 비개발자 친화 재설계 — Room 을 1급으로, 어드민·멤버 한 모델 위에

- 날짜: 2026-08-11
- 상태: **설계 확정 대기** (형 검토 후 계획 문서로)
- 선행: 미리보기를 폰에서 열 경로 정하기 (§선행 의존성)

## 배경

형이 두 가지를 동시에 말했다. **"비개발자가 직접 일을 시킬 수 있어야 한다"** 와 **"나도 헷갈린다"**.
뒤엣말이 핵심이다. 비개발자용 화면만 새로 만들면 형이 보는 화면은 그대로 헷갈린 채 남는다.

헷갈림의 뿌리는 UI 가 아니라 **데이터 모델이 새는 것**이다. 서버가 조각(워크트리·세션들·상태·
링크)을 따로 주고 화면이 그걸 이어붙이니 카드 한 장이 이렇게 나온다:

```
[Claude]  결제 플로우 정리 (쿠폰/구독)          ● 유휴  4일
          claude · mdc-main · 결제 플로우 정리 · mdc-main · payment-flow-coupon-subscription-d023fc
```

이름이 세 번 반복된다. 워크트리 제목과 세션 제목이 **둘 다 "첫 사용자 메시지"에서 나오기 때문**에
거의 같은 문자열이고, 끝엔 해시 붙은 슬러그가 달린다. 워크트리가 대화인지 세션이 대화인지
구분할 근거가 화면에 없다.

관련 코드: `marina_mobile.py` 의 `sessionCard`(제목=`session.title`), `sessionSubtitle`
(부제=`{source} · {alias · sessionTitle · projectLabel · id}`).

## 형이 결정한 것

| 항목 | 결정 |
|---|---|
| 비개발자의 역할 | **직접 일을 시킨다** (관전이 아니다) |
| 채팅방 1개 = ? | **일감(워크트리)**. 세션은 완전히 숨긴다 |
| "일이 끝났다"의 형태 | **미리보기 링크** |
| 새 방 생성 | 비개발자도 만든다. 단 **프로젝트만 고르고 브랜치는 자동** |
| 개발자 기능 분리 | **계정 역할로 자동** (`admin` / `member`) |
| 어드민 화면 | **같이 정리한다** — 멤버만 바꾸면 의미 없다 |
| 어드민의 불편 | **네 가지 전부**: 카드 정보 과다 · 이름 중복 · 목록 김 · 탭 혼란 |
| 배포 권한 | 나중에 비개발자가 질 수도 있다 → **자리만** 만들어 둔다 |
| 웹·모바일 대화창 | **모바일을 기준으로 웹을 고친다** ("웹은 터미널 같아서 눈에 안 들어온다") |
| 방 화면에 보일 것 | 지금 뭐 하는 중인지 · 뭔가 바뀌었는지 요약 · 대화만 깔끔하게 |

미리보기 버튼을 "방 화면에 상시" 로는 고르지 않았다. 완료 신호로는 필요하지만 늘 떠 있을
필요는 없다는 뜻으로 읽고, **완료 카드 안**에 넣는다(§멤버 화면).

## 설계

### 1. Room — 서버의 1급 개념

서버가 조립까지 끝낸 뷰모델을 준다. 화면은 받아서 그리기만 한다.

```
Room {
  id, name,          # 사람이 붙인 이름 하나. 슬러그·해시는 노출하지 않는다
  project,           # 프로젝트 라벨
  status,            # 대기 | 작업중 | 응답필요 | 완료 | 문제  (5개 고정)
  previewUrl,        # 있을 때만
  lastMessage, lastAt,
  canShip            # 지금은 항상 false. 배포 버튼의 자리(§확장 지점)
}
```

**세션은 Room 안으로 숨는다.** 한 워크트리에 세션이 여럿이면 마리나가 최신 것을 골라 이어
붙이고, 화면엔 "대화 하나"로 보인다. **워크트리 = Room = 대화, 1:1:1.**

`status` 를 5개로 고정하는 게 중요하다. 지금은 서비스 상태·에이전트 상태·질문 대기가 서로 다른
어휘로 섞여 있어 화면마다 다르게 읽힌다.

**이름 규칙**: `name` 은 사람이 읽는 한 줄이고, 워크트리 슬러그(`payment-flow-...-d023fc`)는
상세에서만 보여준다. 같은 이름이 반복되지 않도록 서버가 중복을 제거해서 준다.

### 2. 멤버 화면 — 메신저

방 목록 → 방을 열면 대화. 형이 고른 세 가지만 둔다.

```
┌──────────────────────────────┐
│ ← 결제 플로우 정리            │
├──────────────────────────────┤
│                              │
│        (대화만 깔끔하게)       │
│                              │
├──────────────────────────────┤
│ ⚙ 파일 3개 고치는 중…         │  ← 지금 뭐 하는 중인지 (한 줄, 사람말)
├──────────────────────────────┤
│ 메시지 입력…              [↑] │
└──────────────────────────────┘
```

- **진행 표시는 한 줄, 사람말로.** 도구 이름·명령어·경로는 보이지 않는다.
- **완료 카드**: 일이 끝나면 대화 안에 카드가 하나 떨어진다. "뭐가 바뀌었는지" 요약 +
  **[화면 보기]** 버튼(= `previewUrl`). 결과가 나왔을 때만 나타난다.
- 서비스·로그·깃·터미널·연결·compose 는 **없다**.
- **새 일감**: `+` → 프로젝트 하나만 고른다. 브랜치명은 마리나가 첫 메시지에서 짓는다.
  선택지를 프로젝트 하나로 줄이는 게 안전장치다.

### 3. 어드민 화면 — 같은 모델 위에 도구를 얹는다

멤버 화면과 **다른 화면이 아니다**. 같은 Room 위에 도구가 얹힌 형태다.

| 형의 불편 | 대응 |
|---|---|
| 카드 하나에 정보가 너무 많다 | 카드는 **이름·상태·마지막 활동** 셋만. 서비스·에이전트는 방 안으로 |
| 이름이 중복·무의미 | Room `name` 하나만. 슬러그·해시는 상세에서만 |
| 목록이 너무 길다 | 기본 **최근 활동순 + 진행 중만**. 끝난 건 접어둔다 |
| 탭이 많고 어디서 뭐 하는지 | 방 안은 **대화 중심**, 개발 도구는 **접힌 서랍 하나**로 |

서랍 안에 지금의 로그·깃·연결·터미널·서비스가 들어간다. 탭 다섯 개를 항상 펼쳐두는 대신,
필요할 때 서랍을 연다.

### 4. 웹·모바일 대화창 통일

렌더러는 이미 `marina-web/chat-render.js` 로 공유돼 있다(2026-08-03 작업). 벌어져 보이는 건
**웹이 그 위에 터미널풍 스타일을 덮어쓰기 때문**이다. 따라서 로직이 아니라 **웹 CSS 를 걷어내고
모바일 말풍선 스타일로 맞추는** 작업이다. 분량이 작다.

## 선행 의존성 — 미리보기를 폰에서 열 수 있게

§2 의 완료 카드는 **[화면 보기]** 가 폰에서 열려야 성립한다. 지금은 안 열린다.

- 게이트웨이 주소가 `<워크트리>.<프로젝트>.localhost:3902` 다. `*.localhost` 는 폰에서
  **이름 해석 자체가 안 된다**.
- Funnel 이 태우는 건 `/` → `127.0.0.1:3900`(대시보드)과 `/lemon` → `3910` 뿐이다.
  게이트웨이 포트(3902)는 밖으로 나가지 않는다.

`feat/gateway-expose` 브랜치는 이 문제와 **무관하다**. 이미 main 에 머지돼 있고, 거기서 말하는
`expose` 는 compose 서비스 사이의 노출(도메인 모드·CORS)이지 인터넷 노출이 아니다.
(설계 초안에서 이걸 선행 과제로 적었던 건 오판이었다 — 파일명을 잘못 찾아 "미머지"로 읽었다.)

그래서 실제로 정해야 할 것은 **경로 하나**다. 두 가지가 보인다:

1. **대시보드를 통한 프록시** — 이미 Funnel 에 올라가 있고 인증도 걸려 있는 3900 에
   `/preview/<room>/…` 를 만들어 게이트웨이로 넘긴다. 인증·노출 경로를 새로 안 뚫어도 된다.
2. **게이트웨이를 직접 Funnel 에 태우기** — 서브도메인 기반 라우팅을 경로 기반으로 바꿔야 하고,
   인증이 게이트웨이엔 없어서 따로 붙여야 한다.

**1번으로 간다**(형 확인). 인증이 이미 있는 문 하나만 쓰는 게 안전하고, 멤버 역할과도 자연스럽게
맞는다(멤버는 자기 방의 미리보기만 볼 수 있어야 한다).

앱을 어디 새로 배포할 필요는 없다 — 워크트리마다 compose 서비스가 **이미 맥에서 돌고 있고**,
게이트웨이(Caddy)가 맥 안에서 라우팅까지 하고 있다. 없는 건 **밖에서 거기로 들어가는 문** 하나다.

```
폰 → (Funnel) → 마리나 대시보드 :3900 → 게이트웨이 :3902 → 워크트리의 앱
                 이미 공개·로그인 있음      이미 라우팅 함     이미 떠 있음
```

**첫 화면만 넘기면 안 된다.** 웹 페이지는 열린 뒤 JS·CSS·이미지·API 를 계속 더 부른다. 그
요청들이 전부 같은 문을 통과해야 하므로, 단일 페이지 응답이 아니라 **경로 전체를 그대로 넘기는
프록시**여야 한다.

**알려진 위험**: 앱이 `/static/...` 같은 **절대 경로**를 쓰면 `/preview/<방>/` 접두사 아래에서
어긋난다(연결 재설계 때 남겨둔 "잔여 물리" 두 건 중 하나). 실제로 띄워보면 바로 드러난다.
어긋나면 방마다 주소를 따로 주는 방식(서브도메인)으로 돌린다.

## 확장 지점 — 배포

지금은 만들지 않는다. 대신 Room 에 `canShip` 을 두어 자리를 잡아둔다. 나중에 비개발자가 배포를
지게 되면 이 값이 조건을 만족할 때 방 안에 **[반영하기]** 버튼이 뜨는 식으로 붙인다.

지금 만들지 않는 이유: 배포는 사고 시 파급이 크고, 어떤 조건에서 허용할지(리뷰 통과? 테스트
통과? 프로젝트별 정책?)가 아직 정해지지 않았다. 자리만 잡아두면 나중에 UI 를 다시 안 짜도 된다.

## 역할 분리 — 이미 있는 것을 쓴다

`auth.db` 에 `role TEXT NOT NULL CHECK (role IN ('admin','member'))` 와 `project_access`
테이블이 **이미 있다**. 새로 만들 게 아니라 렌더 경로에 연결만 하면 된다.

- `member` 로 로그인 → 방 목록 + 방 화면만
- `admin` 로그인 → 같은 화면 + 도구 서랍
- 멤버는 모드가 있다는 것도 모른다. 형은 필요하면 전환할 수 있다

## 미해결 · 리스크

1. **브랜치 자동 작명의 품질** — 비개발자의 첫 메시지에서 브랜치명을 짓는데, 오작명이 쌓이면
   형이 나중에 정리해야 한다. 규칙(날짜 접두사 + 짧은 슬러그)과 나중에 이름 바꾸기를 함께 둔다.
2. **"완료"의 판정** — 에이전트가 스스로 끝났다고 하는 시점과 실제로 볼 만한 결과가 나온 시점이
   다를 수 있다. 첫 판은 에이전트 상태(`completed`)로 두고, 오탐이 잦으면 규칙을 다시 본다.
3. **미리보기가 항상 있지는 않다** — 서비스가 없는 워크트리(문서 작업 등)엔 `previewUrl` 이
   없다. 그때 완료 카드는 요약만 보여준다.
4. **Room 도입 범위** — 기존 `/api/state` 를 대체할지 병행할지. 병행이 안전하지만 두 벌이
   생긴다. 계획 단계에서 정한다.
