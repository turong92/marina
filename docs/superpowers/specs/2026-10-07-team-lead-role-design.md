**요약.** 역할 규칙은 자리를 잡았고(general-purpose 로 새는 호출 59% → 0%), 기존 여섯 역할로 안 되는 일은 하나만 남았다 — 워크스트림 하나를 통째로 맡아 developer·code-reviewer 를 다시 부르는 **하위 지휘**. 지금은 이걸 general-purpose 로 띄운다(14번). 이 문서는 그 자리에 역할 정본 `lead.md` 하나를 놓고, `/team` 에 "언제 리드를 쓰나·무엇을 넘기고 받나"를 더한다. 리드는 승인된 계획을 실행만 한다: 형에게 묻지 않고, push·merge·배포를 하지 않고, 코드를 직접 고치지 않는다. 진행 상황은 파일에 남겨 재시작 뒤 새 리드가 이어받는다. 규칙 집행은 먼저 **기록 구멍을 메우고 세는 것**까지 — 차단 훅은 1주 숫자를 본 뒤 정한다.

### 0.3 확인 안 된 것 (지어내지 않는다 — 작업 0 에서 한 번 잰다)

1. 이름 붙인 에이전트에 `SubagentStart`/`SubagentStop` 훅이 불리는지, 불린다면 `agent_type` 값이 무엇인지.
2. 이름 붙인 에이전트에 정본의 `effort`·`skills`·`tools` 가 먹는지(모델만 간접 확인됨).
3. `PreToolUse` 훅 입력에 **호출한 쪽이 서브에이전트인지**(agent_id·agent_type) 가 들어오는지 — 리드 안 리드 차단, 서브에이전트의 전체 스위트 거절이 여기에 달렸다.
4. `SendMessage` 로 이어 쓴 에이전트의 stop 이벤트가 몇 번 나고 토큰이 누적인지 구간인지("마지막 구간만 남는 것으로 보인다"는 관찰뿐).
5. 리드가 백그라운드로 부른 자식의 끝 알림이 리드에게 오는지(ovation 지휘 세션이 교체 리드에게 준 프롬프트에 "안 온다"는 관찰이 적혀 있다).
6. 리드가 자기 자식을 `SendMessage` 로 이어 쓸 수 있는지.
7. 조사가 쓴 "구현 묶음"의 정의, 불필요한 질문의 건수(73건 중 "일부").
8. sonnet 리드 14번의 결과물 품질. 일이 끝났다는 것만 안다.

## 1. 목적 · 범위 · 비목표

**목적.** 작업이 많은 워크스트림을 general-purpose 대신 **정해진 역할**로 맡긴다 — 모델·규칙·반환 형식이 정본에 박히고, 기록에 남고, 재시작에 살아남는다. 지휘 세션은 그동안 형과 계속 얘기한다.

**범위.**
1. 역할 정본 `lead.md` 하나(기존 여섯과 같은 모양).
2. `/team` 확장 — 판정표 한 줄, 넘겨받기·점검·교체·끝 보고 대조 절 하나.
3. 넘겨받기 문서·진행 문서의 위치와 최소 형식.
4. role-hook 기록 구멍 수리(이름 붙인 에이전트) — 리드는 항상 이름을 붙여 띄우므로 이게 없으면 새 역할이 기록에서 통째로 빠진다.
5. 세는 도구 하나(`role-report`) — 주간 지표와 "끝 안 난 에이전트" 점검.

**비목표 (이유).**
- **세션 간(채널 간) 상위 PM.** 앞 스펙이 이미 따로 떼어 둔 일이고("프로젝트별 #메인 PM"), 세션끼리 말을 주고받는 수단이 아직 안 정해졌다. 이번 조사에서 필요가 확인된 건 세션 **안**의 하위 지휘 하나뿐이다.
- **일정·우선순위 관리 도구.** 우선순위는 형이 Discord 에서 직접 정한다. 조사에서 병목으로 나오지 않았다.
- **자동 배포·push·merge.** 형 결정 영역이다. 리드는 물론 지휘 세션도 묻고 한다.
- **리드의 리드(계층).** 깊이와 토큰만 는다. 리드는 리드를 부르지 않는다.
- **죽은 에이전트 자동 되살리기.** 못 살린다(10-07 재기동 스펙의 비목표와 같다). 대신 진행 문서로 새 리드가 잇는다.
- **차단 훅(리뷰 누락·3바퀴·전체 스위트).** 이번엔 세기까지. 1주 뒤 숫자로 정한다(§6, 정해야 할 것 8).
- **레포 자체 리뷰어의 모델 맞추기**(mdc-main sonnet). 다른 레포 설정이고 규칙대로 도는 것이다.

## 2. 무엇인가 — 정본 하나 + /team 확장

둘 다 한다. 나누는 기준은 "누가 읽나"다.

| 무엇 | 어디 | 누가 읽나 | 담는 것 |
|---|---|---|---|
| `lead.md` | `shared/agents/` + `~/.claude/agents/` 링크 | 리드 자신 | 리드가 지킬 규칙·돌려줄 것 |
| `/team` 추가분 | `shared/skills/team/SKILL.md` | 지휘 세션(과, 스킬로 실린 리드) | 언제 쓰나·넘겨받기 문서·점검·교체·끝 보고 대조 |

- 새 스킬은 만들지 않는다. 리드는 `/team` 을 `skills` 로 싣고 그중 0(원칙)·2(넘길 것·받을 것)·4(되돌림)만 따른다 — planner 가 brainstorming 을 싣고 "묻는 단계만 건너뛰는" 것과 같은 방식. 되돌림 규칙을 두 군데에 쓰지 않으려는 것이다.
- 이름은 `lead`. 하네스가 지휘 세션을 `team-lead` 라 부르므로 그 이름은 피한다.

### 2.1 지휘 세션과 리드의 경계

| 일 | 지휘 세션 | 리드 |
|---|---|---|
| 형과 대화, 버튼으로 묻기 | 한다 | **못 한다** — `## 정해야 할 것` 으로 올린다 |
| 크기 판정, 워크스트림으로 쪼개기 | 한다 | 안 한다 |
| planner·designer 부르기, 스펙·계획 확정 | 한다 | 안 한다(형 확인이 따라오는 일) |
| 넘겨받기 문서 쓰기 | 한다 | 읽는다 |
| 워크스트림 안 작업 순서 정하기 | — | 한다(계획의 작업 목록 그대로) |
| developer·code-reviewer·qa·researcher 부르기 | 리드 없는 경로에서 | 한다 |
| 구현 → 리뷰 → 수정 회송, 3번 상한 | 리드 없는 경로에서 | 한다 |
| 자식이 오류로 죽었을 때 다시 시키기(한 번) | — | 한다 |
| 리드가 멈췄는지 보기, 리드 교체 | 한다 | — |
| 진행 문서 | 읽고 대조한다 | 쓴다 |
| 끝 검사(전체 스위트 한 번) | 리드 여럿을 나란히 돌렸을 때 | 혼자 돌았을 때(넘겨받기 문서가 정한다) |
| 커밋 | 형이 허락했는지 넘겨받기 문서에 적는다 | 문서가 허용하면 작업마다 developer 에게 |
| push·merge·배포·운영 반영·돈 드는 선택·삭제 | 형에게 묻고 한다 | **안 한다** |
| 형에게 끝 보고 | 한다 | 지휘 세션에게만 |

**"멈춤 감지"의 실제 모양.** 리드는 자식을 포그라운드로 부르므로 자식이 응답 없이 멈추면 리드도 같이 멈춘다. 그래서 리드가 잡을 수 있는 건 "오류로 돌아온 자식"뿐이고, 진짜 멈춤은 **지휘 세션이 리드를 보고** 잡는다(§4.4).

```markdown
너는 리드다. 지휘 세션이 준 **넘겨받기 문서가 정본**이다 — 먼저 끝까지 읽고, 진행 문서가 이미 있으면 그것부터 읽고 거기서 잇는다.

## 규칙
- 실린 /team 의 0(원칙)·2(넘길 것·받을 것)·4(되돌림)를 그대로 따른다. 크기 판정과 형에게 묻기(1·3·5)는 네 일이 아니다.
- **형에게 직접 묻지 않는다.** push·merge·배포·운영 반영·돈 드는 선택·되돌릴 수 없는 일·범위 변경을 만나면 추측으로 정하지 말고 진행 문서의 `## 정해야 할 것` 에 적는다 — 선택지 2~4개, 추천 하나에 (추천)과 이유 한 줄. 그 결정과 무관한 작업은 계속하고, 더 할 게 없으면 돌려준다.
- 부르는 역할은 developer·code-reviewer·qa·researcher 뿐이다. planner·designer·lead·general-purpose 는 부르지 않는다. 역할은 포그라운드로 불러 결과를 직접 받는다.
- 작업 하나마다 developer → code-reviewer. 수정 회송은 **세 번까지** — 네 번째가 필요하면 그 작업을 멈추고 남은 지적을 적는다. 리뷰를 건너뛴 작업은 이유를 진행 문서에 적는다.
- 역할 호출의 `description` 은 작업 키로 시작한다: `T3 구현` · `T3 리뷰 2회차` · `T3 수정 2회차`.
- 코드·설정은 직접 고치지 않는다. 네가 쓰는 파일은 진행 문서뿐이다. 한 줄 수정도 developer 에게.
- **진행 문서**를 역할을 부르기 직전과 결과를 받은 직후에 고친다 — 네가 사라져도 다음 리드가 이어받게.
- 전체 스위트·전체 빌드는 넘겨받기 문서가 "끝 검사는 리드가"라고 했을 때만, 작업이 다 끝난 뒤 한 번.
- 커밋은 넘겨받기 문서가 허용했을 때만 작업마다 developer 에게 시킨다. push·merge·배포는 절대 안 한다.
- 역할이 결과 없이 죽었으면(오류·빈 응답) 새로 한 번 더 시킨다. "막혔다"고 돌려주면 우회하지 말고 그 작업을 멈추고 적는다.

## 돌려줄 것
1. 끝난 것 — 작업 키별 커밋(또는 바꾼 파일)과 리뷰 결과(회차·남은 Minor)
2. 증거 — 끝 검사 명령과 결과 원문 마지막 줄, 직접 확인한 것 / 안 한 것
3. 남은 것 — 안 끝난 작업과 이유
4. `## 정해야 할 것`
5. 방치 없음 확인 — 부른 에이전트가 전부 끝났는지, 남긴 백그라운드 셸·예약이 없는지(있으면 무엇이)
6. 진행 문서 경로
```

- `tools` 줄은 두지 않는다(developer 와 같다). 역할을 부르고 이어 쓰는 도구의 정확한 이름이 이름 붙인 에이전트에서 무엇인지 확인되지 않았고(§0.3-2), 줄을 잘못 쓰면 리드가 아무도 못 부른다. "코드를 안 고친다"는 문구로 두고 기록으로 센다(§6).
- 모델·effort 는 지금 리드가 실제로 돈 값(sonnet)에서 시작한다. 정해야 할 것 2.

## 4. 계약

### 4.1 넘겨받기 문서 — 지휘 세션이 쓴다

위치 `<워크트리>/.superpowers/sdd/<YYYY-MM-DD>-<워크스트림 키>/brief.md`. 한 화면(30줄 안팎). 최소 내용:

1. **목표** 한 줄과 워크스트림 키(예 `w8-video`).
2. **정본** — 승인된 스펙·계획 경로와 맡길 작업 키(`T1`~`T7`). 계획이 없으면 리드를 띄우지 않는다.
3. **범위 / 비범위.**
4. **자리** — 워크트리 경로, 브랜치, 시작 HEAD.
5. **형 결정**(원문) — 이미 정해진 것. 설계 문서와 다르면 이쪽이 이긴다.
6. **권한** — 커밋 허용 여부. 금지: push·merge·배포·운영 반영·돈·삭제.
7. **끝 검사** — 명령과 누가 돌리는지(`리드가` / `지휘 세션이`).
8. **진행 문서 경로**.

레포 규칙·빌드 명령은 옮겨 적지 않고 레포 `AGENTS.md` 를 가리킨다. 리드를 부르는 프롬프트는 한 줄이면 된다: "넘겨받기 문서가 정본이다: `<경로>`".

### 4.2 진행 문서 — 리드가 쓴다

같은 폴더 `progress.md`. 맨 위 다섯 줄 안에 상태 줄이 있어야 한다(점검 명령과 세션 시작 안내가 읽는다).

```markdown
# 진행 — w8-video 영상 파이프라인
상태: 진행 중            (진행 중 | 막힘 | 끝)
리드: w8-video (2026-10-07 14:20~) · 앞 리드: 없음
넘겨받기: .superpowers/sdd/2026-10-07-w8-video/brief.md · 시작 HEAD 8b27073

## 작업
| 키 | 내용 | 상태 | 리뷰 | 커밋 |
|---|---|---|---|---|
| T1 | 영상 테이블·저장소 | 끝 | 2회차 통과 | ab12cd3 |
| T2 | 올리기 API | 수정 중 | 1회차: Critical 1 | (없음) |

## 지금 하는 일
14:52 developer 에게 "T2 수정 1회차"

## 정해야 할 것
## 범위 밖에서 본 것
## 끝 검사
안 돌림
```

- "지금 하는 일"은 역할을 부르기 **직전**에 고친다. 리드가 죽으면 이 줄이 멈춘 자리다.
- 리뷰 칸이 비어 있으면 리뷰가 없었다는 뜻이다. 지휘 세션의 끝 보고 대조가 이 칸을 본다.
- 형식은 이 한 장이 전부다. 도구로 파싱하는 건 상태 줄뿐이다.

### 4.3 리드가 돌려주는 것

§3 의 여섯 항목. 지휘 세션은 **다시 하지 않고 대조만** 한다:
- 진행 문서 작업 표에 리뷰 칸이 빈 "끝" 작업이 없는가(있으면 이유가 적혀 있는가).
- 커밋 범위가 `git log` 와 맞는가.
- 끝 검사 결과가 있는가. 리드가 돌렸으면 다시 돌리지 않는다(전역 규칙 "방금 통과한 테스트를 다시 돌리지 않는다").
- "방치 없음 확인"이 `role-report open` 과 맞는가.

### 4.4 형 결정을 만났을 때 · 멈췄을 때

```
리드가 형 결정을 만남
  → 진행 문서 "정해야 할 것"에 적음(선택지·추천)
  → 무관한 작업은 계속 / 더 할 게 없으면 상태 "막힘"으로 돌려줌
지휘 세션
  → /team 3 대로 형에게 버튼으로 물음(한 번에 최대 4개)
  → 답을 넘겨받기 문서 "형 결정"에 적고, SendMessage 로 같은 리드에게 이어서 시킴
```

```
리드가 소식이 없음
  → 지휘 세션: `role-report open` 한 번 + 진행 문서 "지금 하는 일"
  → 기록이 안 자란 지 오래됐거나 리드가 사라졌으면(세션 재시작) 새 이름으로 lead 를 띄움
     — 같은 넘겨받기 문서, 진행 문서부터 읽게. 진행 문서 "앞 리드"에 교체 이유 한 줄
```

"오래"의 기준은 30분에서 시작한다(지금 방치는 24~64시간). 숫자는 1주 뒤 기록을 보고 고친다.

## 5. 언제 리드를 쓰나 / 쓰지 않나

`/team` 판정표에 한 줄을 더한다.

| 크기 | 기준 | 경로 |
|---|---|---|
| 워크스트림 여럿 | **승인된 계획**이 있고, 작업이 5개 이상이거나 서로 독립인 묶음이 둘 이상 | 기능 하나·구조 변경 경로로 계획 승인까지 → 묶음마다 넘겨받기 문서 → lead → 끝 보고 대조 → 형에게 보고 |

쓰지 않는다:
- 조사만, 작은 수정, 작업 4개 이하인 기능 — 지휘 세션이 직접 부른다(잘 돌아간 `dev-taskN`/`rev-taskN` 방식 그대로).
- 계획이 없거나 형 결정이 남은 일 — 리드는 물을 수 없어 곧바로 돌아온다.
- 한 워크트리에 이미 리드가 돌고 있을 때 — 같은 브랜치에서 둘이 커밋·빌드하면 엉킨다. 나란히 돌리려면 워크트리를 나눈다.
- 리드 안에서 — 리드는 리드를 부르지 않는다.

작업 수 기준(5개)과 세션당 동시 리드 수는 정해야 할 것 6·7.

## 7. 기록 — 먼저 고칠 것

**먼저 고친다.** 리드는 항상 이름을 붙여 띄운다(이어 쓰기·교체 식별). 지금 훅은 이름 붙인 에이전트를 통째로 빠뜨리므로, 그대로 두면 새 역할이 Discord 시작·끝 줄에도 #상태 역할별 사용량에도 안 나온다 — 앞 스펙의 목표("보이게")가 새 역할에서 바로 깨진다.

`role-hook` 이 바뀌는 것(모양만):
- 역할 판정: 훅 입력의 `agent_type` 이 정본에 없으면 meta 파일의 `customAgentType` 을 본다. 그래도 없고 `name` 이 있으면 종류 `teammate` 로 남긴다(버리지 않는다).
- 이벤트에 칸 셋 추가: `name`(붙인 이름) · `parent`(부른 에이전트 id, 없으면 빈 값) · `depth`.
- 호출 기록(`pending`) 짝 찾기가 이름 붙인 호출에서도 되게.
- 이어 쓰기 토큰은 작업 0 의 실측(§0.3-4) 결과대로 — 누적이면 "에이전트당 마지막 stop 만 센다", 구간이면 "더한다"를 집계 쪽 규칙으로.
- 덧붙임: 지금 이벤트의 `model` 칸은 **shared 정본의 값**이고 실제 돈 모델은 `models` 칸이다. 레포 자체 리뷰어(mdc-main)처럼 둘이 다를 수 있다. 집계는 `models` 를 쓴다.

훅이 아예 안 불리는 것으로 드러나면(§0.3-1) 훅으로는 못 고친다. 그때는 `role-report` 가 하네스 기록(meta.json)을 직접 읽는 것으로 대신하고, Discord 줄은 이번 범위에서 뺀다 — 작업 0 뒤에 이 절을 고쳐 쓴다.

## 8. 검증 · 측정

### 8.1 세는 도구 — `shared/bin/role-report`

- `role-report week [--since <날짜>]` — 아래 지표를 한 화면으로. 구조(역할·이름·부모·깊이)는 하네스 기록 meta.json 에서, 시간·토큰은 events.jsonl 에서 읽는다. meta 를 직접 읽는 이유: 이름 붙인 에이전트까지 빠짐없이 있고, 훅을 고치기 **전** 기간(10-04~10-07)도 같은 식으로 다시 셀 수 있다.
- `role-report open [--cwd <경로>]` — 시작 있고 끝 없는 에이전트: 역할·이름·할 일·시작 후 경과·기록 파일이 마지막으로 자란 뒤 경과. 지휘 세션이 손으로 8번 하던 점검을 이 한 줄로 바꾼다.
- 읽기 전용이다. 아무것도 죽이지 않는다.
- 역할별 호출 수·토큰은 넣지 않는다(#상태에 이미 있다).

### 8.2 지표

| 지표 | 세는 법 | 조사 때 | 바라는 방향 |
|---|---|---|---|

1. **역할 이름**
   - `lead` (추천) — 짧고, 하네스가 지휘 세션을 `team-lead` 라 부르는 것과 안 겹친다
   - `team-lead` — 요청의 표현 그대로지만 하네스 이름과 겹쳐 기록을 읽을 때 헷갈린다
   - `pm` — 일정·우선순위까지 맡는 것처럼 읽힌다(비목표)

2. **모델 · effort**
   - sonnet · medium (추천) — 지금 리드 14번이 실제로 이 모델로 돌아 일이 끝났다. 1주 사용량을 보고 올린다
   - sonnet · high — 분해·판단만 조금 더
   - opus · high — 판단은 좋아지지만 리드는 오래 살아 컨텍스트가 길다. 비용이 얼마나 늘지 아직 잰 적이 없다

3. **리드가 코드를 직접 고쳐도 되나**
   - 안 고친다, 진행 문서만 쓴다 (추천) — 역할이 섞이지 않고 "리뷰 없는 구현"을 셀 수 있다
   - 한두 줄(오타·import)만 허용 — 왕복은 줄지만 경계가 흐려지고 그 수정은 리뷰를 안 탄다
   - 전부 허용 — 사실상 오래 사는 developer 가 된다

4. **리드가 planner·designer 를 부를 수 있나**
   - 못 부른다, 승인된 계획만 실행한다 (추천) — 기획·디자인은 형 확인이 따라오는데 리드는 물을 수 없다
   - 부르고 그 "정해야 할 것"을 그대로 위로 올린다 — ovation 리드가 실제로 설계까지 했다. 대신 리드가 형 확인 전에 구현으로 넘어갈 위험이 있다

5. **리드의 커밋**
   - 형이 그 워크스트림에 커밋을 허락했을 때만, 넘겨받기 문서에 적고 작업마다 커밋 (추천) — 작업공간 규칙(명시 요청 없이 커밋 금지)을 지키면서, 리드가 죽어도 끝난 작업이 커밋으로 남는다
   - 커밋 금지, 끝나고 지휘 세션이 한 번에 — 규칙엔 가장 안전하지만 리드가 죽으면 미커밋 변경이 뒤섞여 남는다
   - 리드는 항상 작업마다 커밋 — 이어받기는 가장 쉽지만 작업공간 규칙과 어긋난다

6. **"워크스트림 여럿"의 작업 수 기준**
