# 원격 런타임 — 설계

Date: 2026-08-24

Status: 설계 확정(실측 기반), 구현 착수

## 결정

워크트리별로 **컨테이너가 도는 기계**를 고른다. 로컬(지금 동작)과 원격(사무실 리눅스 박스)이 공존하며,
로컬 경로는 물리적으로 바뀌지 않는다. 파일 동기화 도구(mutagen 등)는 도입하지 않는다 — Docker 표준
기능만으로 충분함이 실측으로 확인됐다.

## 배경 — 왜 필요한가

web 컨테이너 하나가 11GB(실측 피크), startGroup 전체가 18.4GB다. 16GB 맥은 Docker VM 배정이 7GB 남짓이라
**스택 하나가 아예 안 뜬다.** 워크트리 격리가 문제가 아니라 시작이 안 된다. 이 사람들을 위해 런타임만
옮긴다. 사무실 박스는 61GB RAM / 12코어 / Docker 29.4.3 / compose 2.39.4.

## 실측으로 확인된 것 (2026-08-24, mdc 전체 스택 e2e)

5개 서비스(web·user-api·batch·index-api·search-api)를 박스에서 빌드·기동·응답까지 확인했다.
web 실렌더 617KB, user-api `{"status":"UP"}`, 나머지 200.

| 항목 | 결과 |
|---|---|
| `DOCKER_HOST=ssh://` 로 빌드·기동·watch | 전부 동작 |
| watch sync 소스 반영 | ≲150ms |
| watch initial_sync | 4,700파일 253MB → 4초 (≈63MB/s) |
| `docker cp` 로 JAR 주입 | 503MB → 9초 (≈51MB/s) |
| amd64 재빌드(맥은 arm64) | 5개 전부 통과, 이미지 18.7GB |
| 빌드 시크릿(npmrc) | 동작 — 클라이언트가 로컬에서 읽어 API 로 보냄 |
| 포트·게이트웨이·watch·시크릿 | **손댈 것 없음** |

## 두 가지 구조적 제약 (설계를 결정한 근거)

### 1. `--project-directory` 는 이중 역할이다

빌드 컨텍스트와 watch 소스는 **클라이언트**(개발자 맥)에서 읽고, 바인드 마운트 경로는 **데몬**(박스)에서
푼다. 원격이면 이 둘이 갈라지는데 compose 에는 값이 하나뿐이다. 따라서 **바인드 마운트는 원격에서 풀 수
없다.**

"박스에 같은 절대경로를 미러링" 안은 폐기했다 — 박스에 `/Users` 를 만들 수 없다(sudo 불가). 공용 박스에
사용자별 맥 경로를 재현하는 구조 자체도 사람이 늘면 무너진다.

### 2. watch sync 는 "부팅에 필요한 파일" 에 쓸 수 없다

sync 는 **돌고 있는** 컨테이너에 파일을 넣는다. JVM 은 부팅 시점에 JAR 이 필요해 sync 가 도착하기 전에
죽는다(실측 확인: `no jar found in /app/libs`). 닭-달걀이다.

→ 해결: **named volume + 기동 전 `docker cp`**. `docker cp` 는 Docker API 로 흐르므로 원격에서 안전하다.

### 3. 주입만으로는 개발 루프가 안 닫힌다 — watch 규칙도 바꿔야 한다

기동 전 주입은 **부팅**을 해결하지만 **재빌드**는 아니다. mdc 는 `action: restart, path: .../build/libs` 를
선언하는데, 로컬은 바인드 마운트라 새 JAR 이 바로 보이고 restart 로 끝난다. 원격은 named volume 에 기동
시점 JAR 이 들어가 있어 **restart 를 해도 예전 JAR 을 다시 읽는다.**

→ 해결: 원격 오버레이가 **주입된 경로의 `action: restart` 를 `sync+restart` 로 바꾼다.** sync 가 돌고 있는
컨테이너의 그 경로(=볼륨 마운트 지점)에 쓰므로 볼륨에 남고, 이어지는 restart 가 새 파일을 읽는다. 부팅
닭-달걀은 이미 떠 있으니 해당 없다. 표준 compose 기능만으로 닫힌다 — 여기서도 mutagen 은 필요 없다.

범위는 **경로가 정확히 일치하는 규칙**뿐이다. 부모/자식을 추측하면 프로젝트가 선언하지 않은 동작을
만들어낸다. 일치하는 규칙이 없으면 그대로 둔다(로컬에서도 그 경로는 수동이었다는 뜻).
한계: mdc 의 `.env` 는 그 경로에 watch 규칙이 없어(컨텍스트 루트 `.dockerignore` 가 `.env*` 를 제외)
원격에서 변경 반영에 재기동이 필요하다. 설정 파일이라 빈도가 낮아 지금은 감수한다.

## 주입 대상 (실측으로 확정)

원격에서 컨테이너에 **밀어 넣어야** 하는 것:

| 대상 | 크기 | 왜 |
|---|---|---|
| `be-api/*/build/libs` (JAR) | 503MB | 바인드 마운트 + 부팅 필수 |
| `apps/web/.env`, `.env.ssm.local` | 8KB | 바인드 마운트. **watch sync 로 안 넘어감** — 컨텍스트 루트 `.dockerignore` 의 `.env`/`.env.*` 가 하위 경로까지 제외한다(실측 확인) |

**안 넘어가는 것**: `node_modules`·`.venv` 4.8GB. watch ignore 에 양쪽 다 명시돼 있고 컨테이너는 deps 를
이미지에서 받는다. 이건 개발자 맥의 IDE 용이며 로컬에 남는다.

## 설계 — 런타임 타깃

모드 플래그를 코드 곳곳에 흩뿌리지 않는다. **"런타임 타깃" 하나**를 두고 로컬·원격이 같은 인터페이스를
통과한다. 로컬 구현은 전부 지금 동작(대개 no-op)을 반환하므로 **로컬 경로의 물리적 변경이 없다.**

| 인터페이스 | 로컬 타깃 | 원격 타깃 |
|---|---|---|
| `docker_env()` | `{}` | `{"DOCKER_HOST": "ssh://<host>"}` |
| `volume_rewrite(svc)` | 없음(바인드 그대로) | 호스트 경로 바인드 → named volume |
| `prepare(services)` | no-op | `docker cp` 로 주입 |
| `host_memory()` | macOS `sysctl` | 박스 `/proc/meminfo` |

원격을 알아야 하는 곳은 세 군데뿐이다:

1. compose 호출 env — 모든 호출이 이미 `env=env` 를 받는다(`marina-compose.py:893`, `1491`). 초크포인트 1곳.
2. `build_overlay()` — volumes 치환.
3. 기동 시퀀스 — 로컬 `up -d`, 원격 `up --no-start` → `docker cp` → `start`.

## 저장

워크트리별 런타임 타깃은 세션 디렉터리에 둔다(런타임 상태이며 레포 설정이 아니다). 박스 주소 등 프로젝트
공용 값은 `~/.marina/<id>/` — 기존 `build-args.json`·`links.json` 과 같은 자리.

## 기조 유지

**stored compose 수정 0줄, 새 compose 파일 0개.** 원격 델타가 전부 마리나가 생성하는 오버레이와 기동
시퀀스 안으로 떨어진다. 프로젝트는 지금 쓰는 compose 를 그대로 쓴다.

## 비목표

- 파일 동기화 도구 도입(mutagen 등). 실측 결과 자리가 없다. `.env` 양방향이 실제로 필요하다고 밝혀지면
  그 파일 하나에만 재검토한다.
- 로컬 경로를 원격 방식으로 통일. 로컬 바인드 마운트는 비용 0·즉시 반영이라 통일은 순수 퇴보다.
- 공용 박스의 다중 사용자 격리. 포트는 Docker 랜덤 할당이라 충돌하지 않음이 확인됐고(`ports:["8081"]`),
  대상 인원이 1~2명이라 지금은 불필요. 인원이 늘면 별도 안건.
- 프로젝트 메모리 상한. 박스가 61GB 라 현 시점에 전제조건이 아니다.

## 주변부 (구현 완료)

- **메모리 판단이 데몬을 따라간다.** 원격이면 `docker info/stats` 가 박스를 향하고, 호스트 여유는 박스의
  `/proc/meminfo` 를 ssh 로 읽는다. 스냅샷 캐시는 **데몬별로 갈랐다** — 하나를 공유하면 로컬 워크트리가
  채운 값이 원격 질의에 그대로 나간다. 박스를 못 읽으면 로컬 값으로 대체하지 않고 unknown 으로 둔다
  (다른 기계의 숫자로 판단하느니 모른다고 하는 편이 안전하다).
- **PreToolUse 의 "원격=마리나 밖" 예외에 예외를 뒀다.** 원래 취지(원격을 막으면 MARINA_DIRECT 가
  습관이 되어 탈출구가 망가진다)는 그대로 두되, **그 박스가 이 워크트리의 런타임이면** 마리나 관할이라
  막는다. 무관한 기계는 여전히 통과한다.
- **`forward: host` 경고.** 원격에서 `host` 는 개발자 맥이 아니라 박스를 가리킨다 — 같은 선언인데
  기계가 바뀌므로 기동 시 어느 포트가 그런지 알린다. 서비스 타겟(`8081: user-api`)은 컨테이너 DNS 라
  대상이 아니다.

## 스위치

`marina remote use [<host>] [--global]` / `off` / `inherit` / `status`.
`off` 는 **로컬 고정**(전역이 원격이어도 이 워크트리만 로컬), `inherit` 는 **이 계층의 의견을 지움**(전역을
따름) — 다른 뜻이라 둘 다 필요하다. 쓰기는 `write_target()` 한 곳(원자적 쓰기·검증).

대시보드는 **서버 현황(메모리) 영역**에 배지를 둔다(형 판단). 워크트리 카드마다 칩을 다는 것보다 낫고,
무엇보다 **필수**다 — 원격이면 그 영역의 Docker/Host 수치가 이미 박스의 값이라, 어느 기계인지 안 밝히면
표시가 거짓말이 된다. 로컬(기본)이면 배지는 숨는다. 이 워크트리만 전역과 다르면 테두리가 점선이다.
`GET /api/sessions` 의 `runtimeTarget`, `POST /api/runtime-target`(kind·host·scope).

## 남은 작업

- `forward: host` 대상(mdc: redis 6379 · kafka 9092 · milvus 19530)을 박스에 띄우는 **운영** 작업.
- `.env` 는 원격에서 변경 반영에 재기동이 필요하다(위 "주입 대상" 참고).
- 별건(mdc 프로젝트): `ai-api/ai-api` 는 이름을 잘못 준 파이썬 venv 1.8GB. watch ignore 에 `.venv/` 만
  있고 `ai-api/` 가 없어 매 initial_sync 마다 동기화된다.
