## A. 워크트리 단위 + 직접 launch

### 확정된 결정 (2026-07-25 형 답변)

| 질문 | 결정 |
|---|---|
| 진입점 | **둘 다** — 워크트리 카드/행마다 ＋Claude/＋Codex, 그리고 워크트리 생성 팬업에 "생성하고 바로 시작" |

### 기반

`term_open(root, agent_source=..., agent_sid=...)` 가 이미 CLI 를 직접 띄운다(`_agent_cli`). 새 세션은
sid 없이 시작해야 하므로 **sid 없는 launch 경로**가 필요하다 — resume 이 아니라 새 세션.

### 설계

- `POST /api/term/agent` `{root, source}` → `term_open(root, agent_source=source, agent_sid="")`
  - `_agent_cli` 는 `_SID_RE` 로 sid 를 검사하므로, 빈 sid 를 "새 세션"으로 허용하도록 넓힌다
    (`claude` / `codex` 를 인자 없이 실행 = 새 세션).
  - 새 세션의 sid 는 시작 시점엔 모른다 → **입양**(`marina_agent_procs`)이 훅 첫 이벤트에서 붙여준다.
    즉 A 는 이미 만든 입양 기계 위에 얹힌다.
- 웹: 워크트리 카드 헤더에 ＋CC/＋CX 아이콘 버튼 → 호출 후 터미널 탭으로 전환 + 그 tid 포커스.
- 모바일: 세션 리스트를 워크트리 섹션(`<details>`)으로 묶고 섹션 헤더에 같은 버튼.

### 범위 밖

- 워크트리 생성 자체의 UI 는 이미 있다(생성 팬업). "생성하고 바로 시작"은 기존 생성 API 호출 뒤
  위 launch 를 이어 부르는 것으로 충분하다.

## B. 초기 로드 성능

### 진단 (2026-07-27 코드 확인)

- `/api/worktrees` 는 이미 **root 병렬**(ThreadPoolExecutor, 14 roots 4.4s→0.8s)이다.
- 진짜 비용은 **캐시 만료**: `WORKTREE_INFO_TTL = 15s`. 15초마다 한 번은 요청이 전체 재계산(0.8s)을
  기다린다. 부팅 직후(콜드)엔 항상 그 비용을 문다 → 첫 화면이 늦다.
- 계산 내용: root+서브레포마다 `worktree_status`/`repo_last_commit_ts`/`repo_ahead_of_main`/`repo_branch`
  = 전부 git 서브프로세스.

### 설계 — stale-while-revalidate + 부팅 워머

1. `worktree_info` 가 **만료된 캐시라도 즉시 반환**하고, 백그라운드로 갱신을 킥한다(single-flight).
   - `WORKTREE_INFO_MAX_STALE`(기본 120s)를 넘으면 그때만 동기 계산(= 너무 오래된 값 방지).
2. 데몬 부팅 직후 워머 스레드가 모든 root 를 한 번 계산해 캐시를 채운다 → 첫 요청이 콜드가 아니다.

요청 경로에서 git 을 기다리는 일이 사라진다. 응답 크기(35KB)는 그대로 두되, 체감은 대기 제거로 해결.

## C. 모바일 헤더

`.shellRow` 는 `grid-template-columns: 36px minmax(0,1fr) auto`. 마지막 `auto` 가 `.shellActions`(사용량 ●,
서버 N/M) 라서 **카운트 글자수가 늘면 계속 넓어지고** 그만큼 `.project-strip` 이 좁아진다.

### 설계

- 액션 칼럼을 **고정폭**으로 못박고(서버 버튼에 `max-width` + 말줄임), 스트립이 잔여폭을 전부 갖게 한다.
- 서버 카운트는 `tabular-nums` 라 자릿수만 늘지 않으면 흔들리지 않는다 — 상한만 두면 충분.
